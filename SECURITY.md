# Security model

## Trust boundaries

pointsman provides advisory decisions and explicitly enabled bounded evidence workflows. It is NOT a sandbox, authorization system, secret vault, or security classifier. A pointsman result never grants permission to execute code, bypass approvals, merge, deploy, migrate data, or trade. Low confidence, malformed responses and service failure delegate to the original host workflow WITH its existing checks. A caller-supplied `risk` flag is a hint, not trustworthy proof that an action is safe.

The supported threat model covers accidental disclosure, untrusted state, malformed upstream output, unsafe filesystem links, config collisions and ordinary network failures. It does not defend against a compromised OS, root, malicious software running as the same account, a compromised Node runtime, arbitrary hostile modifications of trusted local code/config, or all concurrent filesystem races. Host policies must still limit agent filesystem access and outbound data.

## Credentials

The server reads inherited TYPESAFE_API_KEY first. Environment values are never serialized into generated host configs; Codex receives the variable NAME through env_vars. Claude's stdio child normally inherits its parent's environment. Already-running applications need restart after changing inherited variables.

The optional `key set` command accepts hidden interactive TTY input, never command arguments or stdin pipes. It writes only `POINTSMAN_HOME/credentials.env` (0700 home, 0600 file). The file is plaintext, not encrypted. The managed parser accepts one TYPESAFE_API_KEY assignment; it never evaluates shell syntax. It rejects unsafe links, hard-linked files, weak permissions, wrong file owners and placement beneath a Git worktree. Worktree .env files are never automatically loaded. Do not commit, upload, share or feed this file to an LLM.

A same-user coding agent can potentially read a file that its OS account can read, and inherited environment secrets can reach other child processes. File permissions and skill instructions do not create isolation from that agent. Use a dedicated OS account, host sandbox/file-deny policy, or an approved secrets broker for stronger separation. This project intentionally makes no keychain/encrypted-vault claim.

## Data sent outside the machine

Only the caller-supplied minimal `state`, question instructions/criteria, and model name are sent to TypeSafe. Authorization contains the API key. There is no automatic repository scan, conversation upload, environment dump, file attachment, or analytics service. TypeSafe receives whatever permitted state is sent; provider retention, training and residency terms must be checked independently before sending proprietary or regulated data. No zero-retention guarantee is made.

Before sending, the implementation checks all request fields for the exact active key, common token/private-key formats, password assignments, URL credentials and sensitive object keys. This is best-effort secret screening, NOT comprehensive DLP. Unknown formats, encoded secrets, private business data and personal data may evade it. Minimize data BEFORE constructing the request. Prompt-injection instructions tell pointsman to treat state as data but are not a security guarantee.

## Bounded workflow execution

The optional `run` entrypoint reads source/report files beneath a root fixed by its trusted CLI/MCP/JS caller. Request JSON cannot change that root or supply commands. Repository inventory respects Git ignore rules and refuses nested repositories, links and private paths. Evidence packets include source text, so they belong to the requesting host context, not content-free telemetry. The current three recipes make no provider calls.

JS integrations may inject named, already authorized test callbacks; the workflow cannot authorize those callbacks. OFF/SHADOW performs no source collection. Policy/provider changes, cancellation, source changes and exhausted limits prevent completed results. Original files remain intact. Native adapters can synthesize a completed segment only through a supported host contract and a separate explicit gate; normal permissions and continuation remain with the host. Generic decision qualification does not establish qualification for a new workflow family.

## Source preselection

MCP `collect_evidence` and `read_evidence` share the server's bound root and existing workflow limits, with a separate default-OFF evidence mode; global OFF dominates. Literal terms and relative paths cannot supply regex, shell commands, new roots or permissions. Collection excludes Gitignored files, symlinks, nested repositories, credentials and denied directories including `docs`, `private`, `models` and `.pointsman-local`. Bounded scans and exclusions remain coverage limits. A direct read requires the referenced source hash to match; original files and conversation history remain intact.

Local lexical collection is the default. Explicit semantic selection sends only admitted bounded candidate snippets to the selected provider, never a raw repository or transcript automatically, and uses existing bulk limits and rejection thresholds. Required, uncertain, contradictory, failed and deferred evidence stays recoverable; exhaustive coverage disables filtering. Optional filtering creates no execution authority, credential source or automatic provider fallback. Evidence text belongs to the requesting host; metrics contain only bytes and counts.

## Transport and output validation

The endpoint is fixed to HTTPS `api.typesafe.ai/v1/systemone`. Redirects and endpoint overrides are disabled; insecure TLS disabling is refused by the engine. Node/OS TLS trust remains authoritative. No automatic retries. The default deadline covers the complete response, not only headers. Request/frame/response sizes, question counts, in-flight concurrency and per-process call rates are bounded. Bounded reason codes replace raw errors and upstream error bodies.

Choice answers must belong to the original candidates and have a valid distribution; Score must match a valid bounded expected value; Noul remains a true probability and has no invented confidence. `confidence` is not proof of truth, and formatting correctness is not semantic correctness. Confidence thresholds must be evaluated for each use case. No answer changes the `authorizesExecution: false` contract.

## Local storage and installation

Generated configs contain executable paths and nonsecret variable names/paths only. The installer changes only its named MCP entry, owned skill files, shim and installation records. It refuses collisions and edits it cannot attribute to its previous installation. Writes are atomic and check expected contents; a private lock prevents concurrent installations for the same POINTSMAN_HOME. Failure rolls back its own unchanged writes without clobbering another writer. This is not a globally atomic transaction across independent host processes.

`install --hooks` additionally appends one owned hook group (a fixed `pointsman hook --host --event --home` command, `timeout: 10`) to the end of each owned event's array in Codex `hooks.json` and Claude `settings.json`, and appends one short marked instruction block to Codex `AGENTS.md` and Claude `CLAUDE.md` (user scope only; project scope skips the block). Ownership of a hook group is decided by exact JSON equality to its own previously recorded value, the same way the MCP entry above is owned; every other hook group in the same file, and every other byte of the instruction file outside the marked block, is preserved unchanged. A hook group or instruction block that no longer matches what was last installed is treated as user-modified and the write is refused (`MANAGED_HOOK_CHANGED` / `MANAGED_CONFIG_CHANGED`) rather than silently overwritten. `uninstall` (with or without `--hooks-only`) removes only entries it finds an installation record for; `uninstall --hooks-only` removes hooks and the instruction block without touching the MCP entry, skills, shim or global mode. The installer never writes a host's trust/approval state — Codex `hooks.json` entries still require the user's own `/hooks` approval before Codex will execute them, and the installer never writes `config.toml`'s `hooks.state`; `doctor` only reports whether an entry naming the owned `hooks.json` exists there, without printing it or verifying its hash. Command line/config/log output for `install`/`uninstall`/`doctor` never includes a host config file's full contents (a `settings.json` can carry unrelated environment values); only the owned hook groups it added/removed, their content hashes, and the instruction block text are ever reported.

`install --laya-agent` (macOS only, dry-run reviewed before applying, like every other owned host artifact) writes one user launchd agent plist at `~/Library/LaunchAgents/com.pointsman.laya.plist` (file mode 0600) that runs `pointsman laya serve --home <POINTSMAN_HOME>` at login. The plist carries no secret: its `EnvironmentVariables` is only `POINTSMAN_HOME`, never `TYPESAFE_API_KEY` or any credential. `KeepAlive.SuccessfulExit:false` restarts it only after an abnormal exit, never after the server's own clean SIGTERM/SIGINT shutdown. `uninstall --laya-agent` removes only that plist file (never the MCP entry, hooks, skills, shim or global mode) and never runs `launchctl` itself; the report gives the exact `launchctl bootstrap`/`bootout` commands for the user to run. The resident server listens only on a local Unix domain socket at `POINTSMAN_HOME/run/laya.sock` (directory 0700, socket file 0600, verified after `listen()`), never a network port or HTTP endpoint; a same-OS-user threat that can already read `POINTSMAN_HOME`'s other private files is outside this boundary, consistent with "Trust boundaries" above. Each connection is a one-shot JSON-line request/response (max 64KiB per frame) and the server logs only content-free events (event name, latency, bounded reason code) — never the request `state`, `questions` or `answers` — the same discipline as "Logs, retention and rotation" below. An existing socket path is reclaimed only after a live-probe confirms nothing is listening and the path is actually a Unix socket owned by the current user; a symlink, a regular file, or a socket owned by another user is refused rather than replaced.

Backups are private files under POINTSMAN_HOME/backups with a path manifest. **They are copies of existing host configuration and may contain other credentials already present there.** Never print their contents or put them in Git. Partial directories may remain after a failed installation. A crash can leave install.lock; only remove it manually after verifying no installer is active. Do not overwrite a host's trust/approval settings or instruct it to bypass sandbox restrictions.

OFF is checked before network use and again before applying an in-flight answer. It cannot recall already transmitted data or cancel provider billing. Native host/server disable is stronger than logical OFF for removing tool-discovery overhead. POINTSMAN_DISABLE=1 is process-inherited, not a live environment broadcast. User and project installs share state when POINTSMAN_HOME is the same; separate processes do not share request counters.

## Logs, retention and rotation

Only time, random decision ID, mode, purpose, bounded reason code, numeric latency/usage/counts and application eligibility are logged. No state, prompts, candidate names, chosen values, source, keys, raw exception messages or hashes of user content are persisted. Short-lived feedback keeps normalized decisions in process memory for at most five minutes between accesses, with a 128-entry cap; process exit clears it. Logs use private JSONL files with a roughly 10MiB/day cap and best-effort writes. They are not automatically deleted. Metrics read at most 30 days but do not enforce retention.

Revoke a suspected key in the TypeSafe account, set OFF, update the environment or use key set, remove obsolete credentials and restart inherited host processes. `key remove` removes only the managed file, not provider access, shell history, backups or inherited environments. Never paste incident secrets into GitHub issues or chat. Report security issues privately to the repository owner; do not include real keys or proprietary payloads.

## Supply chain

Node >=22 and built-in modules only. No runtime npm packages, install hooks, shell-evaluated credentials, remote bootstrap execution, background updater or public HTTP listener. Dependencies can be added only after a separate review. CI uses commit-pinned actions, read-only repository permission, no persisted checkout credential and no TypeSafe key. The manual MCP stdio subset is covered by protocol tests but is not certified full-protocol compliance; actual target clients remain a separate acceptance check.
## v0.3 training capture is a separate opt-in data boundary

Operational telemetry still stores no raw state, questions or answer values. Explicitly enabled Training Capture may persist bounded sanitized content to private files OUTSIDE Git. It is OFF by default, is not encrypted storage, and performs no upload/training. Every export row is screened; regex detection is not complete DLP. Capture permission must cover the complete inference interval. Model comparisons need explicit remote consent. MCP outcomes and the `training outcome` CLI's stdin JSON are always weak host-review evidence, never runner/human attestations, regardless of what `source`/label values the caller supplies. Laya starts only a locally configured Python/runtime/checkpoint with allowlisted environment, no inherited API/HF secrets, no shell, no network download, and no automatic CPU fallback acceptance. Same-OS-user tampering is outside the threat boundary.

Strong (`objective`/`human`) labels can only be created through: an in-process library caller that owns its own runner (`store.outcome()`, e.g. a directly integrated executor); `pointsman runner verify`, which runs only a command an operator pre-registered from an interactive terminal with `pointsman runner allow` (the agent selects a registered name, never the argv, labels, or pass/fail mapping); and `pointsman training correct`, an interactive human-correction prompt. `runner allow`/`remove` and `training correct` all require both stdin and stdout to be a TTY. **A TTY check is a same-OS-user local-authorship signal, not proof of a human operator** — a PTY-attached coding agent also has a TTY, and this is not a defense against that same-OS-user threat, consistent with the "Trust boundaries" section above. `runner verify` never lets its command's stdout/stderr, or a caller-supplied exit code/label, reach storage: pointsman runs the registered argv itself with `stdio: 'ignore'` and derives the recorded label only from the process it started. A timeout, spawn failure or signal death records a failed command check but no label, and the command runs without `TYPESAFE_API_KEY` in its environment. Changing the dataset minimum-label gate also requires a TTY.

Independent synthetic corpora use the separate in-process `writeIndependentDataset` path with declared source rights, an oracle revision and family lineage. This is authored-rule evidence, not a human or registered-runner attestation. The included generator independently recomputes its gold; arbitrary caller assertions do not establish semantic correctness. New four-way exports retain legacy source-rights UNKNOWNs instead of converting them into permitted data.

## Distributing and adopting a Laya checkpoint through Hugging Face

`pointsman laya package` never uploads; it only writes a local folder (`pointsman.json` plus the registered checkpoint's own files, symlinks refused) that the operator uploads themselves with `hf upload`. It refuses an unqualified candidate (`NOT_QUALIFIED`) and never writes task text, labels, local absolute paths, the configured Python path or device into the manifest — only file hashes/sizes, the same qualification fields `providers.json` already accepts, and content-free evaluation counts.

`pointsman laya pull` requires a full 40-hex commit sha (`PINNED_REVISION_REQUIRED` for a branch/tag) and validates the fetched manifest with the exact same `validateProviderConfig` the runtime loader uses before touching disk. It follows redirects manually, one hop at a time, re-checking the destination host against an allowlist (`huggingface.co`, `*.huggingface.co`, `*.hf.co`) before every request (`UNTRUSTED_DOWNLOAD_HOST` otherwise) — an `HF_TOKEN` from the environment is attached only when that hop's host is exactly `huggingface.co`, decided fresh at each hop rather than carried over from a header it received, so it cannot follow a redirect (for example to an LFS host) off that host. Every downloaded file is streamed to a private temp path (directory 0700, file 0600) under a size cap taken from the manifest and renamed into place only after its sha256 matches; a mismatch aborts without registering anything. The manifest itself is capped at 256 KiB. Registration reuses the existing `register` fingerprinting path; if the recomputed fingerprint does not equal the manifest's declared checkpoint, `pull` fails with `CHECKPOINT_MISMATCH` and removes any candidate copy it just created (a previously registered, unrelated checkpoint that happens to collide is left untouched). `HF_TOKEN` is never included in `pull`'s output, and the CLI does not expose any option to point it at a host other than Hugging Face's.

`pointsman laya adopt` lets a consumer without a local holdout activate a pulled candidate using the qualification the publisher included in the manifest (`laya/published/<checkpoint>.json`), instead of running its own `qualify`/`compare`. This is a distinct trust decision from `promote` — the qualification numbers are taken on faith from the publisher, not independently reproduced — and it still only ever writes through the same atomic, `validateProviderConfig`-checked path as `promote`/`activate`, never changes the selected provider, and is undone by the same `rollback` stack.
